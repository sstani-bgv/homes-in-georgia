# Оценка поиска: llm vs hybrid (21.10.2026)

Скрипт: `test/eval_search.py` (копия базы в `/tmp/eval_search` из `listings.json`: 410 опубликованных, 468 с векторами;
живая база и `.env` не трогаются). 13 запросов + 2 продолжения («ещё», ❤️/👎 + «ещё»), каждый в трёх режимах:

- **llm** — как сейчас: весь каталог (~410 строк) в Codex + отдельный вызов на место;
- **hybrid** — один короткий вызов Codex (место + бюджет/спальни/районы/животные/стиль), фильтры в коде, ранжирование
  локальными векторами, Codex выбирает 5 из 20 и пишет причины;
- **hybrid, final_llm=off** — то же без второго вызова: топ-5 по баллу, причина из профиля квартиры.

Нарушения считаются по условиям, заданным в скрипте вручную (не по тому, что извлекла модель), так что ошибки
извлечения тоже были бы видны. Глазами: `proof/eval/qNN.png` — по 5 фото с ценой на режим, красная рамка = нарушение.

**Фото клиента.** Фото квартиры из базы (q10) — исходник на 1-м месте во всех режимах. Скриншот (обрезка 75%, 512 px,
q11) — исходник на 1-м месте во всех режимах (векторное сходство 0.94 против ≤0.82 у остальных). В первом прогоне q11
с бюджетом «до 2000$» исходник ($2700) честно не показался ни в одном режиме.

**Вкус (❤️/👎, q03).** После лайка и дизлайка следующие 5 по фото ближе к понравившейся, чем к отвергнутой, во всех
режимах; сильнее всего без финального Codex (0.886 против 0.762), но тогда все 5 оказались из одного канала
(один фотограф и водяной знак «CRESCO» тянут вектор) — разнообразия меньше.

**Качество на глаз** (листы `proof/eval/`): hybrid с финальным Codex по стилю не хуже llm (q03, q04, q06, q12: те же
или очень похожие квартиры), а q02 llm отдал только 2 карточки (строже трактовал «с балконом»), hybrid — 5 без
нарушений. Без финального Codex подбор по стилю заметно грубее (в q03 «сканди + растения» попала классика с
ковром), причины шаблонные («Светлая квартира с …» из профиля), понятый запрос — из первого вызова.

## Рекомендация

Переключить на **hybrid** с `final_llm=on`: те же 0 нарушений, ~3 из 5 совпадают с текущим режимом, остальное
сопоставимо на глаз, промпт в 12 раз меньше (лимиты подписки), ответ быстрее (≈24 с против ≈40 с, «ещё» ~11 с).
`final_llm=off` — запасной режим при упоре в лимиты или если нужен ответ за ~8 с: условия соблюдаются так же,
но стиль и причины слабее. Перед переключением один раз: `.venv/bin/python embed.py` (~2.5 мин на 468 объявлений).

## Модели (выбор)

Разовый тест без LLM на тех же 410 объявлениях: (1) фото 0 → остальные фото той же квартиры,
(2) русская фраза «как выглядит» из профиля → фото этой квартиры, (3) P@20 по стилю (лофт, классика, сканди…).

| модель | фото→та же квартира MRR | ru-текст→фото MRR | стиль P@20 (en, 6 стилей, сумма) | скорость, 1224 фото |
|---|---|---|---|---|
| CLIP ViT-B/32 + clip-ViT-B-32-multilingual-v1 | 0.44 | 0.09 | 1.65 | 45 с |
| SigLIP 2 base 224 (google/siglip2-base-patch16-224) | 0.54 | 0.31 | 2.00 | 97 с |
| **SigLIP multilingual base 256** (google/siglip-base-patch16-256-multilingual) | **0.60** | **0.33** | **2.05** | 138 с |
| jina-clip-v2 | не запустилась с transformers 5 (нужен старый transformers) | | | |

Выбрана multilingual SigLIP: лучшая по всем трём, обучена на многоязычных подписях (ru/en/ka), один вектор на фото и
текст. Отдельная текстовая модель (e5/bge-m3) не добавлялась: профиль квартиры уже сравнивается текстом SigLIP
(вес 0.4), а все жёсткие условия решает код; места для заметного выигрыша на этой оценке не видно.
