# End-to-end тест полной версии: отчёт (21.10.2026)

**Итог: 16 из 16 сценариев прошли.** Всего 201 проверка (assert), ещё 8 информационных: они касаются качества выбора
модели и на результат не влияют. Подбор шёл через настоящий Codex: 11 вызовов, 234 с. Unit-тесты (`test/`, 21 шт.)
и `ingest.py --test` тоже зелёные.

Запуск одной командой из корня проекта:

```bash
.venv/bin/python test/e2e/run.py              # настоящий Codex для подбора (~11 вызовов, ~6 мин)
.venv/bin/python test/e2e/run.py --fake-llm   # детерминированная заглушка вместо Codex (~2 мин), для отладки
```

## Как устроен тест

- **Бот.** Настоящий `bot.py` (`build()` → `run_polling()`) работает отдельным процессом. Вместо Telegram у него
  локальный фейковый Bot API (`test/e2e/fake_tg.py`). В `bot.build()` для этого добавлен крючок: если задан
  `TG_API_BASE`, бот ходит на `base_url`/`base_file_url` по этому адресу; в проде переменной нет, и ничего не меняется.
  Фейковый сервер отвечает на `getMe`/`getUpdates`/`getFile`, раздаёт фото, которые «прислал» клиент, и записывает
  каждый исходящий вызов: `sendMessage`, `sendMediaGroup` (с самими фото), `editMessage*`, `answerCallbackQuery` и т.д.
  Сценарии подают апдейты от имени симулированных пользователей: текст, команды, фото, `web_app_data`, нажатия
  кнопок, сообщения в группе. Проверки идут по записанным вызовам и по базе.
- **Окружение.** Всё лежит в `/tmp/e2e`: копия базы `app.db` (собрана через `db.py sync` из текущего `listings.json`),
  рабочая папка, логи. Тестовые `AGENT_CODE` и `ADMIN_PASSWORD` берутся из окружения теста. `.env`, `data/app.db`,
  живой бот и настоящий Telegram API не трогались, Apify и сборщики не запускались.
- **Codex.** На `PATH` стоит прослойка `test/e2e/codex_shim.py`. Она записывает каждый вызов модели (промпт, фото,
  ответ) и передаёт его настоящему `codex`. По этому журналу проверяется, что попало в каталог подбора.
- **Админка.** Настоящий `admin.py` запускается на свободном порту поверх той же копии базы и проверяется в headless
  Chrome (Playwright).
- **Mini App.** `webapp/index.html` открывается в Chrome. `telegram-web-app.js` подменён заглушкой, которая
  записывает `sendData` и рисует MainButton; поиск места (Nominatim) тоже подменён. Payload, полученный из Mini App,
  дальше используется в сценарии 3 с картой.
- **Скриншоты.** Переписки рендерятся в стиле `proof/render.py`: шапка «Homes in Georgia», ширина 880 px. Видны
  нажатия кнопок, всплывающие ответы и правки карточек на месте.

## Найденные баги

### Исправлены

1. **Агент, добавленный в админке по @username, не получал лиды.** Админка обещает, что Telegram id «привяжется при
   первом сообщении боту», но привязка (`core.agent`) вызывалась только на командах и кнопках агента. Агент, который
   просто нажимал /start или писал боту, оставался без `tg_id` и не попадал в рассылку. Исправление: в `bot.py`
   добавлен `bind_agent()` в `on_start` и `on_message`. Доказано сценарием 12: после /start id привязан, следующий лид
   пришёл этому агенту.
2. **Кириллица в английских карточках:** площадь выводилась как «68 м²». Исправление: в `core.py` добавлена единица
   `sqm` в тексты ru/en (`m²` для en). Доказано сценарием 6: в английских карточках нет кириллицы.
3. **Канал агентства дважды опубликовал одну квартиру, и клиент мог увидеть её два раза.** Это `tg539434`/`tg539415`:
   Самгори, 87 м², одни и те же 3 фото. Дедуп в `ingest.py` склеивал только копии с разных сайтов. Исправление:
   внутри одного источника объявления склеиваются, если у них 2+ общих фото. Одно общее фото (например, снимок
   дома) не склеивает, на реальной базе это проверено: склеилась ровно эта пара, три пары с одним общим фото остались
   раздельными. Добавлены тесты в `ingest.py --test` и в сценарий 13. **Важно:** `listings.json` в этом тесте не
   пересобирался (ingest не запускался), поэтому дубль исчезнет из базы после следующего `refresh.sh`.
4. **Ответ модели «Понял: …» не проходил фильтр утечек.** Описания и «почему подходит» фильтр `public()` проходили,
   а `understood` нет; если клиент сам напишет сайт или телефон, модель могла их повторить. Исправление: в `core.py`
   фильтр применяется и к нему. Это укрепление по ТЗ п. 3; в прогоне такая утечка не наблюдалась.

### Не исправлено (требует решения, а не мелкой правки)

- **Водяные знаки на фото раскрывают источник.** На части фото с myhome.ge и у агентств-конкурентов видны логотипы
  (например, «myhome.ge» на 3-й карточке в `06_english.png`, «TC City» на 5-й). Текстовая проверка утечек этого не
  ловит. Варианты: обрезать или замазывать водяной знак при ingest, не показывать такие фото или распознавать их
  моделью при индексации.
- ~~Смена статуса в админке не обновляет уже отправленную карточку лида в Telegram.~~ Исправлено вместе с панелью
  агента: админка и панель правят все копии карточки через Bot API (сценарий 17).
- **PTB предупреждает:** `review_loop` создаётся в `post_init` через `app.create_task` до старта приложения. Цикл
  работает, рассылка на проверку в сценарии 7 прошла, но при остановке остаётся «Task was destroyed but it is
  pending». На работу это не влияет.

## Что осталось недоказанным

Настоящая доставка через Telegram (бот и Mini App внутри клиента Telegram), запись в настоящую Google-таблицу,
карта или ключ агентства (сейчас OpenStreetMap и Nominatim), живые сборщики (сайты, каналы, Apify) и расписание
`refresh.sh`, работа сервера 24/7. Всё остальное по 16 пунктам ТЗ проверено локально на настоящих `bot.py`,
`admin.py`, `core.py`, `db.py`, `sheets.py` и `webapp/index.html`.
